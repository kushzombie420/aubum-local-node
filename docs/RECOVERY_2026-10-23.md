# Shared-GPU Recovery and Manual Mode Control — 2026-10-23

**Scope:** Sanitized public case study of the private Aubum prototype, October 17–23, 2026.

**Result:** Live operation was restored for standard MUSIC, PHOTO, and VISION on a shared GPU worker. Manual selection from the MAIN machine was demonstrated through the existing worker controller. This report is **not** an installation guide or a claim that unattended handoff, protected XL Turbo activation, or every possible mode transition is complete.

## Context and impact

Aubum is a local-first distributed AI prototype spanning different consumer devices. One managed GPU workstation, referred to privately as Herman, serves several GPU-intensive creative capabilities. Only one of the competing large workers should own GPU resources at a time.

During work on Qwen Image 2.1, ACE-Step XL Turbo, transport ownership, and protected startup, multiple generations of launchers, guardrails, manifests, and recovery packages accumulated. New protection work became difficult to integrate with retained legacy startup behavior. Extensive isolated tests passed, but production readiness remained blocked by unresolved bindings, identity evidence, startup compatibility, and approval requirements.

The practical consequence was an extended period in which the developer could not reliably use the intended chat-based creative workflows. The presence of working individual components did not establish a reliable end-to-end operational path.

## What went wrong

Several interacting issues emerged:

- **Competing startup assumptions:** Recovered launchers referenced legacy locations while staged protected components expected different startup locations and source pins.
- **Ownership and state mismatch:** The older XL ownership/bootstrap flow required a particular available-state transaction; the manual recovery was starting from a different, closed-session condition.
- **Incomplete deployment closure:** The protected activation candidate required precise runtime hashes, task and source backups, bindings, and permissions that were not all finalized for the live environment.
- **Misleading progress signals:** CPU-only fixtures, source parsing, and hash checks proved useful properties, but a long series of offline PASS reports did not mean the complete worker could safely be activated.
- **Tool/backend mismatch:** Later, after standard MUSIC was restored, the Open WebUI music tool still targeted XL Turbo. Its ownership claim returned a conflict and left a deliberately held local job lock, blocking another generation.

These are interacting failure classes, not evidence that one model or one machine was universally broken. The unactivated protected deployment was preserved rather than forced into production.

## Recovery decision

The team of developer and AI assistants narrowed the active objective to **restore reliable creative use first**. Instead of deploying the unfinished protected system, recovery reused the existing worker controller and verified its live status and mode endpoints.

The adopted operating model was:

1. Finish current requests and preserve wanted outputs.
2. Observe the selected mode and verify the relevant worker identity.
3. Explicitly select one of MUSIC, PHOTO, or VISION.
4. Refuse or stop on unexpected/conflicting state rather than stacking GPU workers.
5. Validate the result with a real generation or inference request through the normal interface.

A legacy MUSIC process was stopped during a supervised quiet window only after controller, executable, creation-time, listener, and observed-child checks. Its exit, controller IDLE mode, and GPU memory release were observed. This establishes a useful supervised transition; it **does not** retroactively provide lifetime process containment or a universal guarantee that every detached descendant was absent.

Importantly, this particular recovery avoided invoking the older /mode/idle endpoint, whose implementation could affect multiple workers and clean temporary output folders. The existing worker controller still has shutdown and temporary-output cleanup behaviors, so manual switching is not safe to treat as an unattended, always-non-destructive action.

## October 23 live verification

The following checks were observed through the actual private system, not inferred solely from an offline test suite.

| Check | Evidence/result | Limit |
| --- | --- | --- |
| MUSIC → PHOTO | Controller returned verified Qwen Image 2.1 mode; competing MUSIC listener absent. | Transition initiated after a supervised MUSIC exit. |
| PHOTO generation | Two real image requests completed in Open WebUI and returned saved image outputs. | No public/private images included in this report. |
| PHOTO → MUSIC | Controller returned verified standard MUSIC mode, with Qwen stopped. | This was the standard ACE-Step worker, not protected XL Turbo. |
| MUSIC engine | A song generated successfully in the native ACE-Step interface. | Shows the engine worked independent of the chat tool. |
| Music tool recovery | After the failed XL claim was investigated, the held local lock was archived under guarded checks, the existing tool's backend set to legacy, and Open WebUI returned playable audio. | This did not repair or activate the XL ownership protocol. |
| MAIN manual controls | Remote status and both MUSIC ↔ PHOTO selections succeeded from MAIN. | Operator approval and idle-job assumptions remain required. |
| MUSIC → VISION | The existing VISION mode started, and controller verified the worker. | Other transitions involving VISION were not all live-tested. |
| VISION inference | The normal attached-image inspection tool executed on the VISION worker and returned specific visual observations. | General natural-language tool selection can still depend on prompt wording. |

The result demonstrates **practical recovery for three creative modes** and chat-path generation/inference. It does not establish full crash recovery, unattended multi-job scheduling, safe mid-generation switching, or a protected XL Turbo cutover.

## What remains unfinished

- **Unattended shared-GPU handoff:** Deferred; explicit operator selection remains the working baseline.
- **Protected XL Turbo startup and native containment:** Staged research and older successful XL media tests are retained. The protected manual activation candidate was not live-promoted in this recovery.
- **Automatic job completion proof:** The MAIN control prompts the operator to confirm work is finished. Controller readiness is not an independent guarantee that all callbacks, children, and requests are quiescent.
- **Temporary output safety:** The old controller may remove temporary MUSIC API output directories when switching away from MUSIC. Saved media should be preserved before changing modes.
- **Transition-matrix completeness and reboot behavior:** The documented live tests cover specific paths. This checkpoint is not a full post-reboot acceptance test of all modes.
- **Public release:** The working private selector is machine-specific. A generic, configurable public example requires separate sanitization, documentation, and tests.

The older public VRAM helper is illustrative and invokes /mode/idle; it should not be read as a universally safe substitute for a verified, workload-specific manual transition.

## Engineering lessons

**End-to-end evidence beats a stack of PASS labels.** Unit and fixture tests are necessary for parts of the design; they are not proof that production wiring is correct.

**Complex safeguards require their own integration discipline.** More authentication, source identity, and rollback logic can reduce some risks while creating new failure modes if legacy contracts are not reconciled.

**Preserve known-good paths.** Existing models, worker programs, and working source were retained while the recovery focused on the smallest operational boundary.

**Manual control is a legitimate engineering outcome.** Where automatic handoff is not trustworthy, explicit user-directed selection can be more reliable and transparent.

**AI-assisted development needs scope control.** AI tools helped investigate and recover the system, but also contributed to expanding the integration effort. Human operator observations and acceptance criteria were essential to deciding what to stop developing and what to restore.

**Separate private prototype claims from public reproducibility.** A successful private deployment does not automatically make every function publicly downloadable. Reusable interfaces and independent tests will be released only after they are safe and portable.

## Publication boundary

This case study intentionally omits private addresses, personal data, generated personal images and audio, API keys, certificates, authorization material, service-account details, complete native logs, private database state, and machine-specific backup locations.

The October 9 recovery baseline and earlier dated XL Turbo tests remain part of the historical record. This document records the **current October 23 recovery path**, not a retrospective rewrite of those prior verifications.
